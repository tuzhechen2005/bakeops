# BakeOps 产品文档

> 版本：v0.1（2026-10-20，设计拷问后定稿）
> 状态：开发前基线。后续修改记在 `DECISIONS.md`。

## 1. 一句话

**粘贴当天的订单，告诉我几点开工、按什么顺序做、每单几点能好；顾客来问时间或加单时，告诉我能不能答应。**

英文版（文章与界面用）：
*Paste today's orders. Get a baking plan that fits one person and one oven. When a customer asks "when?" or "can I add more?", get an answer you can actually keep.*

## 2. 用户

**唯一的 v1 用户：一个人经营的小面包工作室老板（也就是作者本人）。**

- 当天现场打面，忙的时候一天打四缸。
- 只有一台烤箱，它同时也是发酵箱：在发酵时不能烤，在烤时不能发酵，切换模式要降温或预热。
- 每款面包共用同一种基础面团，区别在分割、整形、馅料和装饰。
- 订单按天记录（现在写在本子上），没有固定取货时间。
- 顾客通过微信问"几点能拿"、要求"几点前要"、临时加单或取消。

**真实痛点**（作者原话整理）：
- A. 订单一多做不完，不知道还能不能接新单。
- B. 不知道先打哪缸、几点开工、哪盘先进炉。
- C. 顾客问几点能拿，只能估，常常估不准。

## 3. "偷懒"的收益（本周主题）

| 现在 | 用 BakeOps |
|---|---|
| 早上在脑子里排四缸面、三次发酵和一台烤箱 | 粘贴订单，确认一张计划 |
| 顾客问时间，手上沾着面团心算 | 粘贴消息，看答案，点"已发送" |
| 加单时凭感觉答应，下午才发现做不完 | 系统说能不能，以及最早几点 |
| 答应过别人的时间，被新单挤掉 | 已答应的时间受保护，系统不会偷偷挪 |

## 4. 主流程

### 4.1 早上：生成当天计划

1. 把当天订单以文字粘贴进来（从本子抄到手机备忘录，或直接打字）。
2. 模型把文字拆成订单表，每行标注来自原文哪一句。品项对不上目录、数量或时间解析不了的行标红，不猜。
3. 你在表格里改正，点"导入"。
4. 系统按固定规则装盘、分缸，再用求解器排出时间线：开工时间、每一步的时间、每单完成时间、收工时间。
5. 计划以"候选方案"形式展示，你确认后才成为"当天正式计划"。

### 4.2 白天：处理一条顾客消息

1. 选择这条消息来自哪位顾客（必选，不让模型猜），粘贴消息原文。
2. 模型输出结构化理解：意图、对应哪笔订单、要求的时间、加的品项。歧义时停下来问你，不猜。
3. 你确认理解结果。
4. 系统计算：
   - **问时间**：从正式计划查出这一单的完成时间。
   - **要求某时间前**：检查能否做到，不能就给出最早时间。
   - **加单**：检查能否塞进今天，能就给出新计划和差异；不能就说明卡在哪。
   - **取消**：释放未开始的工作，已打好的面团记为余量。
   - **改数量 / 换口味等**：按店规"预订后不可更改"生成回复，不动计划。
5. 展示：原消息、理解结果、新旧计划差异、受影响订单、回复草稿。
6. 你点"批准"，计划才更新。你自己把回复发给顾客后点"已发送"，回复里的时间才变成**承诺**。

### 4.3 执行中：记录真实进度

- 每一步可以点"开始""完成"。已开始的步骤不能被算法改动。
- 演示与测试用一个可设置的模拟时钟。

## 5. 核心概念

- **承诺（Promise）**：只有你把含具体时间的回复标为"已发送"后才产生。没有承诺的订单，系统可以调整顺序；有承诺的订单，新方案必须守住。顾客提出的时间只是"请求"，不是承诺。
- **候选方案 vs 正式计划**：生成建议不等于执行。两者在界面上视觉分开。
- **已发生的事实**：已开始或已完成的步骤，其实际时间、所用面团不可被改写。
- **三种结果**：
  1. 找到并通过校验的方案；
  2. 按你录入的参数，**做不到**（给出最早可行时间或说明今天塞不下）；
  3. 规定时间内**没找到**方案（不能说成"做不到"）。

## 6. 范围

### v1 做（P0）
- 订单文字粘贴 → 模型拆表 → 人工确认导入
- 当天计划生成：打面、一发、分割滚圆、二发、整形、三发、烘烤、冷却、包装
- 烤箱模式（发酵 / 烘烤）互斥与切换时间
- 一个人手的占用冲突
- 发酵后等待窗口
- 消息意图：问时间、要求时间、加单、取消；其他意图按店规回复
- 承诺保护、候选与正式分离、批准前重新校验
- 执行记录与模拟时钟
- SQLite 持久化、幂等、重启恢复
- 模型评测集与结果表

### 以后（P1/P2）
- 取消后余量自动用于新单（P1）
- 消息的英文释义（P1，便于评审观看）
- 拍照识别手写本子（P2）
- 参数配置界面（P2，v1 用配置文件）
- 多天排程、改到明天（P2）
- 原料库存（面粉、黄油等）（P2）
- 同一步骤的备选做法，比如室温发酵代替烤箱发酵（P2）

### 明确不做
- 付款
- 配送路线
- 改配方
- 让模型决定发酵时间、判断食品安全
- 自动给顾客发消息（系统只生成草稿，你自己发）

## 7. 底线（任何功能都不能违反）

1. 不改错订单：顾客身份由你选，订单对不上就停下来问。
2. 不挪动已经发生的生产事实。
3. 不把未经你批准的建议当作已执行。
4. 不为了新顾客偷偷挪动已承诺给老顾客的时间。
5. 你没确认过的参数，系统不替你猜：你先填一个估计值并标为"未确认"，每条依赖它的说明都会写出"此参数未确认"。（原来的"等待窗口默认 0"在单腔烤箱里会让任何一天都排不出来，见 `DECISIONS.md` D24。）
6. "做不到"只说"按现在的分缸方式和参数做不到"，不说绝对做不到；"没找到"永远不说成"做不到"。

## 8. 为什么必须用开放模型

- **顾客隐私**：订单里有顾客名字和习惯，留在店里的电脑上。
- **厨房断网也能用**：本地推理，不依赖网络。
- **零调用成本**：每天几十条消息，不按条付费。
- **模型可替换**：模型输出必须通过程序校验，排程正确性不依赖模型。换 Gemma 的尺寸或版本，只需重跑评测集。
- **可审计**：提示词、评测集、校验规则全部开源，别的面包师可以按自己的品项改。

## 9. 推广性（文章中一句话点出，不为此加功能）

底层结构是：一个人 + 一台需要切换模式的关键设备 + 不能等太久的步骤 + 聊天里答应的时间。家庭烘焙、蛋糕工作室、私房菜都是这个结构。所有步骤、设备、品项都来自配置，代码里不写死任何面包名。

## 10. 成功标准（提交前）

- 演示脚本 `DEMO_SCRIPT.md` 全部场景可在一次录屏里跑通。
- 评测集上：加了程序把关后改错订单的次数为 0；单靠模型时，歧义消息停下来提问的比例 ≥ 90%。
- 校验器独立检查每一个被批准的计划，0 违规。
- 作者在至少一天的真实订单上用过（写进文章的 Lazy Payoff）。
