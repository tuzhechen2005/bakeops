# 演示脚本

> **以下所有时长、容量、时间都是软件测试用的虚构数值，不是烘焙建议。**
> 精确的时刻由求解器算出。周六（T8）先用种子数据跑一遍，调整参数直到每一幕出现预期的**结果类型**，再把实际时刻填进本文并锁定为回归测试。

## 种子数据（`demo/seed.yaml`）

- 厨房配置：同 `DOMAIN.md` 第 1 节示例；四款产品：红豆包、奶酪包、肉松包、奶油餐包，每个 60 g，每盘 12 个。
- 顾客全部为化名。

**粘贴用的订单原文**（模仿作者本子的连写方式，故意包含中文数字、同一顾客两次下单、一条看不懂的记录）：

```
周六：张三 红豆包4个 奶酪包4个 李四 奶酪包六个 王五 肉松包8个 赵阿姨 奶油餐包12个 小陈 红豆包6个 肉松包4个 周老师 奶酪包4个 奶油餐包6个 吴姐 红豆包10个 郑先生 肉松包6个 小林 奶油餐包8个 冯奶奶 红豆包4个 奶酪包2个 陈哥 肉松包4个 周老师 红豆包2个 老褚 那个照旧
```

预期拆出 12 单（周老师两单），"老褚 那个照旧"进入 `unparsed`。你手动补成"奶酪包 6 个"，共 13 单。

合计：红豆包 26、奶酪包 22、肉松包 22、奶油餐包 26，共 96 个、10 盘（红豆包和奶油餐包各 3 盘，其余各 2 盘）、5,760 g 面团。按"每缸最多 3 盘"（D25）分成 **4 缸**（3、3、2、2）。按测试参数，这样的一天约 17:07 收工（T2 实测）。

> **T13 调种子时注意**：4 缸已经接近一天的上限，第 4 幕"加单能帮忙"可能因为太满而变成"做不到"。如果这样，先把种子订单减到约 6–7 盘（3 缸），让烤箱留出空档。演示要的是每一幕出现预期的结果类型，而不是这一份订单本身。

## 第 1 幕　06:00　早上：粘贴订单，得到一天的计划

1. `demo/reset`，时钟设为 06:00。
2. 粘贴原文 → 订单表出现，每行能看到原句；老褚一行标红，写着"看不懂，请手动填写"。
3. 补填后导入 → 初始计划候选出现：
   - 几点开始打第 1 缸、几点打第 2 缸
   - 烤箱泳道上"发酵"和"烘烤"两种颜色交替，中间有切换间隔
   - 每单完成时间、收工时间
4. 批准 → 变成正式计划。

**要讲的一句话**：*"This used to be 20 minutes of mental math every morning."*（真实时长以你自己的经验为准）

## 第 2 幕　10:30　生产进行中

1. 时钟设为 10:30，点"按计划推进到现在"（演示按钮：把计划上 10:30 前应开始 / 完成的步骤记为开始 / 完成）。
2. 时间轴上，已开始的步骤显示为实心、带锁；未开始的为虚线。

## 第 3 幕　10:35　顾客问时间

**3a. 王五**："今天几点能拿？"
→ 理解为 `ask_ready_time` → 显示王五的完成时间 → 回复草稿 → 你点"已发送" → 王五的时间变成**承诺**（时间轴上出现锁形标记）。

**3b. 王五**："那改成总共10个吧"
→ `change_quantity` → 不动计划，生成店规回复："不好意思，预订后数量不能更改哦，取货时间可以帮您调整～"

**3c. 周老师**："四点能拿吗？"
→ 周老师今天有两单 → 界面要求你选是哪一单（模型的猜测只高亮，不生效）。
→ "四点"：04:00 不在营业时间，只剩 16:00，无需追问。
→ 你选第一单 → 结果为可行。

## 第 4 幕　10:45　加单，能帮忙

**赵六**（新顾客）："能加6个奶酪包吗？三点前要"
→ `add_items` + `request_ready_by 15:00`
→ **预期结果：可行**。差异面板显示：
- 赵六新增，完成时间早于 15:00
- 某一两位**没有承诺**的顾客完成时间推迟 N 分钟
- 王五、周老师：不变（已承诺，守住）
→ 批准 → 回复 → 已发送 → 赵六获得承诺。

## 第 5 幕　11:00　反转：知道自己做不到

**孙七**："我要4个红豆包，一点前能拿吗？"
→ **预期结果：做不到**。
→ "相关事实"面板列出：
- 已打好的面团都已分配，余量为 0；孙七的红豆包需要放进一缸还没开始打的面（可能是第 4 幕为赵六新开的那一缸）
- 一缸面从打面到包装的最短链：打面 → 一发 → 分割 → 二发 → 整形 → 三发 → 预热 → 烘烤 → 冷却 → 包装，按测试参数合计 202 分钟，从 11:00 开始最早也要 14:22，已经晚于 13:00（这是严格下界，不依赖求解器，所以这一幕一定是"做不到"）
- 烤箱在某时段被已开始的步骤占用（已发生，不能动）
- 已答应王五、周老师、赵六的时间不能推迟
→ 系统同时给出替代方案："最早 Z 点能好，要按这个时间吗？"
→ 批准替代方案 → 回复草稿写的是 Z 点。

**要讲的一句话**：*"It didn't bend to make the new customer happy. It told me exactly why, and offered the earliest time I can actually keep."*

## 第 6 幕　11:10　取消：已发生的事实不会凭空消失

**李四**："不好意思今天不要了"
→ `cancel`（整单，奶酪包 6）
→ 李四的奶酪包所在缸已打面、所在盘还没整形 → 面团余量面板出现"第 N 缸 余 360 g"（6 × 60 g）
（调种子时确认：11:10 时李四那一盘确实"已打面、未整形"。如果不是，换一位符合条件的顾客，或调整第 6 幕的时钟。）
→ 盘的个数减少；没有任何东西"变回面粉"。
→ 批准。

（P1 加分版：再演示孙七改为 Z 点前的方案会优先使用这 360 g 余量，最早时间提前。）

## 第 7 幕　可靠性（快剪）

1. **过期方案**：生成一个候选，时钟拨快 10 分钟，再点批准 → "这个方案要求 11:15 开始整形，现在已经 11:25，请重新计算"。
2. **双击批准**：同一个方案连点两次 → 只产生一个新版本。
3. **重复消息**：把王五的消息再粘贴一次 → "这条消息 10:35 已处理过"。
4. **重启**：在终端杀掉服务并重启 → 计划版本、承诺、执行记录、面团余量全部不变。

## 录屏要求

- 时长 3–4 分钟，英文字幕；每条中文消息在字幕里附英文意思。
- 开头 15 秒：你真实的厨房或本子照片（不拍顾客信息），一句话说明你是谁、痛点是什么。
- 结尾：评测结果表（来自 `eval/holdout.jsonl`）。
